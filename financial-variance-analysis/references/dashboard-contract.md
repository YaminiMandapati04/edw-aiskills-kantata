# Dashboard contract: the Finance diagnostic renderer

Renderer **1.8.1** reads payload contract **sda.finance-analysis/1.4.0** and admitted diagnoses of contract **sda.finance-diagnosis/1.3.0**, one per view (each carries the written executive summary and decisions, `readout.summary`, which the page shows in place of the engine's bullets); the Month and Year-to-date views on the page's basis are required (`--allow-missing-review` publishes without them, with a visible notice). It refuses anything else. The page embeds a **read-view** of the payload (`scripts/finance/embed.py`), sized for the 16 MB Artifact limit: fields this renderer never reads are dropped (stage A, lossless; the test renders the page from the view and from the full payload and compares every lens and every drill-down; on the Oct-26 extract it takes the page from 16.0 MB to 5.4 MB). If the page would still exceed the limit, accounts immaterial in every lens lose their drill-down evidence and pattern / run-rate detail (stage B), and a page still over the limit is refused with gate `size`. What is on screen is what is in the payload; the full payload on disk is the audit record. **If you change the JS to read a new field, check it is not dropped in `embed.py`**: a field in a drop list is kept automatically when its name appears in the JS (the render JSON's `embed.kept_by_guard` names it), but keys inside the reduced blocks (explanations, run-rate, pattern tests) are keep-lists and need adding by hand.

The assets are never edited for one engagement. Everything variable travels in the payload. A change to an asset is a renderer change: bump `VERSION`, run `scripts/test_finance_pipeline.py`, and read the headless DOM check.

## 2. The separation of powers

The renderer performs **no analytical computation**. It never derives a variance, never infers a classification, never fills a blank, never calls a model. The complete list of arithmetic it may do:

| # | Where | Permitted | Why it is presentational |
|---|---|---|---|
| 1 | every chart | geometry of bars, lines and labels | scaling, not economics |
| 2 | account and driver trend | sum of engine-emitted monthly series over a driver's accounts | aggregation of emitted values |
| 3 | Drivers subsidiary lens | sum of engine-emitted per-subsidiary facts (actual, comparator, variance each emitted per account) | no variance is derived from an actual and a comparator |
| 4 | run-rate bars and ranges | the display-sign flip of a profit-oriented figure | sign convention |

Unavailable is never zero: `null` renders `—`, `no budget`, `not calculated`, `withheld`, `not proposed`. Every proposal carries its state ("proposed · awaiting disposition", "forecast: proposal only, credit 0"); nothing reads as assigned, approved or verified.

## 3. Payload structure

```
contract_version          "sda.finance-analysis/1.3.0"
meta                      title, view, data_mode, currency, as_of{label,start,end,year,quarter,month,name}, primary_lens, scope{subsidiaries, filtered_to, note, accounts, unmapped, excluded_subsidiaries, excluded_reasons, label, account_grain, hierarchy, drill_dimensions},
                          periods[], months_of_history, generated_at, sign_convention{…, by_measure, mismatch}, budget_check{sections, reliable, failed, rule}, materiality, sources, renderer_version, window_labels, basis_labels
accounts[]                id (a + 12 hex: account number + name within subsidiary, or across subsidiaries when budget_grain is 'account'), name, number, subsidiary (null when pooled), subsidiaries[], keys[] (CHART_OF_ACCOUNT_KEYs = classes), budget_grain (subsidiary | account), budget_held_at[], section, l2..l6, driver_ref, display_sign, series{actual, py, budget, variance_vs_budget}   (display basis: costs positive)
unmapped_accounts[]       accounts left out of every total
drivers[]                 id, label, section, accounts[], level (L4 | account)
statement_series[]        monthly actual / py / budget / yoy_pct / margin_pct per statement line
signals{<account id>}     runrate{months, mean, min, max, stdev, cv, reference, reference_basis, resid_stdev, eligible, reason}, tests[]{id, label, state, evidence, note}, fired[], persistence_hint, confidence, volatility
lenses{<WINDOW_basis>}    eight lenses: available, range, lines[], totals{cost_variance, below_line_variance}, kpis[], accounts[] (+ movement, movement_basis, movement_tier), drivers[] (+ movement, movement_basis, movement_tier, one_sided_movement, two_sided_movement, share_scope: ebitda | below_ebitda; share_of_abs_variance is within that scope, so each bridge adds up to 100%), facts{columns, rows},
                          reconciliation{<driver>: total, total_basis, items[]{account, movement, movement_basis}, other{count, movement}, start, end, by_department{comparable, foots_on, rows[]{name, actual, comparator, movement, movement_basis, accounts[], accounts_other}, other, total}},
                          hierarchy{<driver>: driver, levels[], nodes[]{id, level, name, parent, accounts[], actual, comparator, actual_po, comparator_po, variance, variance_pct, movement, movement_basis, share_of_driver, children[]{same, minus share}}, total, unsplit_accounts[]}
                          product_lines{level, items[]{id, name, level, driver, driver_label, actual, comparator, actual_po, comparator_po, variance, variance_pct, movement, movement_basis, share_of_revenue, share_of_movement}, total, basis}
                          splits{<account>: subsidiary | class | department {comparable, foots_on, rows[], other, total, zero_count}}, by_subsidiary (all accounts, profit-oriented; reconciliation[*].by_subsidiary per driver, same shape), bridge{start, end, steps[] (value = driver movement), control, to_net_income},
                          concentration, layers (MTD_budget only), patterns[], insights[], actions[], explanations{accounts[], drivers[], lines[], summary}, readout, story{lead, lines[], growth, accounts}, kpi_diagnoses[], headline{text, slots},
                          summary{lead, insights[], year}: each {id, tone, head, text, claim, drill{level: section | driver | line | outlook, ids[], support[]}, evidence, numbers[]}; actions[] carry ask{text, numbers, one_off_month}
outlook                   fiscal year, periods, lines{rev, ebitda, ni}{ytd, fy_budget, mechanical{rule, run_rate, value, sensitivity[]}, gap_vs_budget, prior_year_full_year}, persistence_view[], note
qc                        status, checks[], caveats[], unmapped_accounts[]
capabilities              price_volume_mix, fx, dimensions, hierarchy_below_l4, transactions: state and reason
analysis_hash             SHA-256 of everything above; the diagnosis binds to it
diagnosis (render only)   the admitted diagnosis plus admitted_at and warnings
```

`story` (added in 1.1.0) is the net-income-first executive narrative for the lens. `lead`: net income vs the comparator, the same window against the other comparator, and how Adjusted EBITDA, synergies and non-operating items split the movement. `lines[]`: one sentence each for revenue, cost of sales, operating expenses, Adjusted EBITDA (with EBITDA and gross margin), synergies when material, and non-operating, each with `top_driver`. `growth`: revenue, cost of sales and opex growth on prior year from the longest available prior-year lens, plus the engine's `operating_leverage` / `cost_growth_outpacing_revenue` reading when fired (`pattern{id, reading, source}`). `accounts`: how many accounts moved, adverse vs favourable, and the top three with their share of the gross movement. Every piece carries its own `numbers[]` register and is checked by the validator (I6); wording is chosen from signs and the monitoring threshold only. `kpis[]` also gains `cogs` and `nonop` in 1.1.0.

Paths follow `lenses[MTD_budget].drivers[d:cos:recurring-cogs].variance`: `[x]` selects a dict key or the list element whose `id` is `x` (or the integer index). Account ids changed in 1.2.0 (they are no longer chart-of-account keys); read them from `accounts[]` or the brief.

**1.5.0** adds the view's `COA_MAPPING_L5` / `L6`: per lens, `hierarchy{<driver>}` (L5 nodes, each with its L6 children and accounts, valued like a driver; a level that repeats its parent is collapsed; a node with no activity in the window is absent; I13 checks that every level foots to its parent on actual, comparator and movement and that no node repeats its parent's name) and `product_lines` (the deepest revenue sub-groups, footing to revenue). At the top level, `nodes[]` (id, driver, section, level, name, parent, accounts) and `product_lines{level, items[]{id, name, level, driver, parent, series{actual, py, budget}}}` (monthly, profit-oriented), and `accounts[].node_path`. QC gains `l5_footing` and `l6_footing`. The renderer (1.9.0) adds the By sub-group drill (L4 › L5 › L6 › account) in the driver panel and drawer, and the `node:` drawer. Renderer 1.9.1 takes the Revenue by product line and Operating expenses by sub-group panels off the Drivers tab (the sub-groups stay in the driver drill; `product_lines` stays in the payload for the brief and the reviews), and draws the driver drawer's comparator-to-actual waterfall with the top three accounts plus one Other step, keyed 1, 2, 3, Other on the axis with the account names, amounts and colours in a key below the chart.

**1.4.0** adds, per lens: `materiality` (the window's own thresholds: `months`, `executive_abs`, `management_abs`, `monitoring_abs`, `management_pct`; validated as the month's set times the months), `sign_flip` on every account, driver and line value (a percentage is then `null`), `one_offs` (`items[]` with `account`, `name`, `driver`, `section`, `month`, `actual`, `reference`, `amount`, `test` of `outlier_month` or `single_posting`, `offset_with` on a cancelling pair; `named[]`, `named_total`, `underlying_variance`; I12 checks the test, the totals and underlying = net income less the named amounts). In `meta`: `materiality.by_window`, `materiality.pct_of_window_revenue`, `build_date`, `data_age_days`, `data_age_warn_days`, `target_date_rule` and `assumptions[]` (`group`, `rows[{label, value}]`, already formatted: the Assumptions dropdown). In `outlook`: `one_offs_excluded[]` and `one_offs_rule`; every rule's `how` says when one-off months were taken out. In `qc.checks`: `window_tie_out` (now a PASS / NOT_RUN statement that windows are sums of `TOTAL_MTD` over months tied to the governed roll-ups; it no longer compares the view's `_QTD` / `_YTD` / `_LTM` columns, so carries no `items[]` or `tolerance`). At render: `diagnoses{lens: diagnosis}`, `review{required, admitted, missing}`; `diagnosis` stays as the primary view's for older readers. Engine prose is linted with the diagnosis gate's causal and forbidden-phrase rules (I6).

**1.3.0** adds `other.items` to every reconciliation and split remainder (the members it groups; validated to foot) and, per run-rate rule in `outlook.lines[*].mechanical.sensitivity`, `path`, `months_used`, `how`, `remaining_value`, `remaining_effect`, `gap_vs_budget` and `gap_vs_prior_year` (I8 checks the path and the identity per rule), and `outlook.gap_view` (per rule: drivers with `run_rate`, `remaining_value`, `remaining_budget`, `remaining_effect`, `persistence_hint`, and totals by section and category; I8 checks that the EBITDA and net-income totals equal the rule's remaining effect).

**1.2.0** adds account identity at number + name within subsidiary, `movement` / `movement_basis` on accounts and drivers (rankings and bridge steps use movement), `reconciliation` and `splits`, the engine-built `summary` with claims and drill targets, `actions[].ask`, and the scope label. The validator adds I10 (every drill table foots to the cent; account movement = actual − comparator) and I11 (summary provenance, drill targets resolve, claims agree with the numbers).

## 5. Interaction rules and must-nots

- When `meta.budget_check.reliable` is false, every budget view (Summary and Drivers) and the Outlook tab show a "Budget not meaningful" note naming the failed lines; the figures still render, the note says they reflect the budget load, not performance.
- Window (Month, Quarter to date, Year to date, Last twelve months) and comparator (Budget, Prior year) switch between the eight precomputed lenses; nothing is recomputed. Period and scope are fixed displays; to analyse one subsidiary, rebuild with `--subsidiary`.
- The admitted diagnosis applies to one lens (its points merge into that view's summary, panels and review sections; no "AI reviewed" badge is shown); every view carries the data badge **Data verified** (when the extract ties to the governed roll-ups), **From the data** (when that check did not run) or **Test data**.
- Summary has only small charts (margin gauges, the diverging movers bars). The EBITDA bridge appears only on Drivers; the full-year bridge only on Outlook.
- The subsidiary lens on Drivers never changes the scope.
- No fourth tab. A coverage or quality problem surfaces through the existing components: the QC badge and drawer, caveats beside the numbers they qualify.
- Progressive disclosure: executive summary (net income first, then the lines and drivers behind it) → P&L strip → movers and decisions → drawer. A reader never needs a drawer to learn the direction of the result or the three largest drivers.
- Wording: negatives print in brackets `(45)`, never with a minus; `favourable` / `unfavourable` / `in line`, never "adverse"; `mn` not `mm`. Visible wording is plain language: no "engine", "payload", "comparator", "mechanical" or "admitted" reaches the page (the headless test refuses them); engine prose passes through `clean()`, which also maps those terms, for the same rules. Labels are limited to direction (favourable, unfavourable, in line, ahead, behind), persistence (one-off?, recurring, new level, seasonal, timing) and publication state (engine baseline, admitted diagnosis).
- Offline single-file HTML: zero external requests, no CDN, no webfont fetch. The test asserts no `src="http` / `href="http`.
- Must-nots the test asserts: no `undefined`, `NaN`, `[object Object]` or "adverse" in the DOM; at least two waterfalls; every region populated; a `null` budget never shown as `$0`.

## 6. Badges

There is **no status banner** under the header: it was removed from every dashboard. The publication state lives in the data badge and the tags. The data badge in the tab bar reads "Data verified · N notes" and opens the data-checks drawer, whose checks carry plain names and OK / Note / Failed / Not run.

Tags carry state, never inference: direction (`favourable`, `unfavourable`, `in line`; `ahead` / `behind` on KPI drawers), persistence (`One-off`, `Recurring`, `New level`, `Seasonal`, `Timing`, `No budget line`), publication state (`Data verified` green, `From the data` amber, `Test data`), `for discussion` on forecast assumptions. Decisions always read "for discussion" with suggested owners; forecast carry always reads as a proposal that nothing enters until an owner accepts it. The glossary at the foot defines each tag.

## 7. Changing the renderer

1. Edit the asset in `artifacts/finance_analytics/` for everyone, never for one request.
2. If the payload shape changed, bump `CONTRACT_VERSION` in `scripts/finance/__init__.py` and the check in the JS; if only presentation changed, bump `RENDERER_VERSION`. Update `VERSION`.
3. Run `python scripts/test_finance_pipeline.py --keep --out work/test` and open the rendered files; the headless DOM check must pass.
4. Keep the allowlist in §2 true. When the payload gains content, the question is which existing component expresses it, not which panel to add.
